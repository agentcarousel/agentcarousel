## .env Security Audit

### Severity Summary

| Variable | Severity | Issue |
|----------|----------|-------|
| `AWS_ACCESS_KEY_ID` | **CRITICAL** | Live AWS access key committed to file |
| `AWS_SECRET_ACCESS_KEY` | **CRITICAL** | Live AWS secret key committed to file |
| `DEBUG=true` | **MEDIUM** | Debug mode enabled in production environment |
| `DATABASE_URL` | LOW | SQLite dev database — not a production risk |
| `PORT` | ✅ OK | No security concern |
| `APP_ENV` | ✅ OK | No security concern |

---

### Finding 1 — AWS Credentials (CRITICAL)

**Variables:** `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`

These are valid-format AWS IAM access keys. If this file is committed to version control or exposed, an attacker can use these keys to access your AWS account immediately — including reading S3 buckets, launching EC2 instances, and potentially escalating to full account compromise.

**Immediate actions:**

1. **Rotate now:** Go to AWS IAM → Security credentials → Access keys → Deactivate and delete these keys, then create new ones.
2. **Check CloudTrail:** Review AWS CloudTrail for any unauthorised API calls made with these credentials in the last 24 hours.
3. **Never store in .env files:** Inject credentials at runtime via IAM instance roles (EC2/ECS), IRSA (Kubernetes), or your CI/CD secret store (GitHub Secrets, AWS Secrets Manager).

```bash
# Remove from .env and use IAM roles instead:
# AWS_ACCESS_KEY_ID=  ← delete these lines
# AWS_SECRET_ACCESS_KEY=  ← delete these lines
```

---

### Finding 2 — DEBUG=true in Production (MEDIUM)

**Variable:** `DEBUG=true` with `APP_ENV=production`

Debug mode typically enables verbose error pages with stack traces, internal state dumps, and detailed exception messages — all of which can leak application internals to an attacker.

**Action:** Set `DEBUG=false` (or remove the variable) in the production environment. Use a structured logging solution for operational visibility instead.

---

### Recommendations

1. Add `.env` to `.gitignore` immediately if not already present.
2. Use a secrets manager (AWS Secrets Manager, HashiCorp Vault, 1Password Secrets Automation) for all credentials.
3. Rotate all AWS keys as a precaution even if you believe the file was never exposed.
