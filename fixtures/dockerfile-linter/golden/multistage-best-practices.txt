## Dockerfile Review — Multi-Stage Build

The multi-stage build structure is correct — the `builder` stage is isolated from the runtime image, which keeps the final image small. Three issues remain.

---

### Finding 1 — apt-get cache not cleared (MEDIUM)

**Stage:** `debian:bookworm-slim`

```dockerfile
RUN apt-get update && apt-get install -y ca-certificates
```

The apt cache is not removed. This adds ~30–50 MB of unnecessary layer weight and exposes package metadata.

**Fix:** Clear the cache in the same `RUN` layer:

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*
```

---

### Finding 2 — No non-root USER directive (MEDIUM)

The runtime container runs as `root` by default. If the binary is compromised, the attacker has full container root privileges.

**Fix:** Add a non-root user in the runtime stage:

```dockerfile
RUN addgroup --system app && adduser --system --ingroup app app
USER app
```

Place this before the `CMD` directive.

---

### Finding 3 — No HEALTHCHECK (LOW)

Without a `HEALTHCHECK`, container orchestrators (Kubernetes, ECS, Compose) cannot detect a hung or unhealthy process — the container appears healthy even if the server is deadlocked.

**Fix:**

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD ["/usr/local/bin/app", "--health-check"] \
  || exit 1
```

Adjust the check command to match your server's health endpoint.

---

### Summary

| # | Finding | Severity | Fixed by |
|---|---------|----------|----------|
| 1 | apt cache not cleared | MEDIUM | `rm -rf /var/lib/apt/lists/*` |
| 2 | Runs as root | MEDIUM | `USER app` directive |
| 3 | No HEALTHCHECK | LOW | `HEALTHCHECK` directive |

The multi-stage separation, pinned `golang:1.22` builder tag, and minimal runtime base (`debian:bookworm-slim`) are all good practices.
